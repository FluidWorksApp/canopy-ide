Canopy 0.5.1 shows what's actually free in a shared cloud workspace and who is using it, and explains features that are waiting on Canopy's server instead of showing an error.

### Cloud workspaces
The resource chip in the status bar now shows what's free in a cloud workspace and how much of it is yours, for example **You 3.4 GB · 20.8 GB free · 6.0 cores free**. Before, it counted files the system had cached as memory in use, so a workspace could look nearly full when most of its memory was free. That cache is now listed apart, as reclaimable: the system frees it automatically as soon as anything needs the room. The chip turns amber when less than 15% of the workspace's memory is free and red under 7%. It also turns amber when less than one core has been free for a while.

Click the chip to see what's available now, then who is using it: you, each teammate by name, and the workspace's own services (its desktop, browsers and Canopy). Each row shows the memory and CPU that person's terminals use. Terminals Canopy can't match to a person, such as ones started from an older Canopy, are listed as other terminals. Per-person usage needs your workspace's latest image; on an older image, the chip shows the workspace total as before.

On your own computer, the chip now also shows how much of the computer's memory is free, next to what Canopy uses.

### Features waiting on Canopy's server
Readable links, **Add funds** and **Request more credit** need an update to Canopy's server. Until that update is live, they now say the feature isn't available on the server yet and that it will start working on its own, instead of showing an error.

### Jobs from other machines run in the right project
When an agent sends a job to your other machine or to a teammate, the job now carries the repository it is about, for example **FluidWorksApp/cause-api**, and the folder the agent was working in. Canopy reads this from the agent's own checkout. An agent can also name the repository, or several when the work spans more than one. Only the repository's address is sent, never a folder on your computer.

On the receiving side, Canopy runs the job in your project whose repository matches, whatever you named the project or wherever you keep it. The job card says **Runs in cause-api (matches FluidWorksApp/cause-api)** and has no project to choose. A job from a teammate still waits for your approval. If you have the repository checked out more than once, for example as a main checkout and a worktree, the main checkout is picked and you can change it.

If you don't have the repository, the card says **You don't have FluidWorksApp/cause-api open here** and offers to clone it. If the job carries no repository, the card says **No project attached to this job**. In both cases no project is selected and **Approve and run** stays off until you pick one. Jobs from your own other machine still start without asking when their repository is open here; when it isn't, or no repository is attached, they now wait for you in the same way instead of starting in another project. Jobs from an older Canopy carry no repository and always ask.
